# tbd wire protocol, version 1 (frozen)

This document expands BRIEF §3. It is shared by the Go daemon (`internal/proto`) and the Android
app (`android/app/src/main/java/io/github/alien2003/teamsbridge/proto/`). Both implementations are
tested against [`vectors.json`](vectors.json), which is generated by the Go side
(`mise run gen-vectors`). **Any change to anything below is a protocol version bump** (`v`, the
QR prefix, the AAD and the HKDF `info` strings all carry the version).

There is exactly one direction: daemon → FCM → phone. No reverse channel exists.

## 1. Pairing secret and code

* `S` — 16 bytes from a CSPRNG (`crypto/rand`).
* Code — RFC 4648 base32 of `S`, uppercase alphabet `A–Z 2–7`, no padding → 26 characters.
  The last character carries 3 data bits and 2 zero bits; decoders accept only the canonical form
  (non-zero trailing bits are rejected), so every secret has exactly one code.
* Displayed as `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX`.
* Input: dashes and spaces are ignored and case is folded; an optional `tbd:v1:` prefix (any case) is
  stripped, so a pasted QR text also works.
* QR text: `tbd:v1:<26 chars>`.

## 2. Keys and topic

`HKDF` is HKDF-SHA256 (RFC 5869) with an **empty salt** (equivalent to 32 zero bytes).

| Value | Definition | Size |
|---|---|---|
| `K` | `HKDF(ikm=S, salt="", info="tbd-enc", L=32)` | 32 bytes |
| `topic` | `base64url_nopad(HKDF(ikm=S, salt="", info="tbd-topic", L=24))` | 32 chars |

The topic matches FCM's topic syntax `[a-zA-Z0-9-_.~%]{1,900}`. It is derived from the secret, so it
is unguessable without `S`; Google sees it, but cannot link it to a person or read anything sent to it.

## 3. Message JSON

```json
{"v":1,"t":"msg","id":"<uuid v4>","ts":1767225600,"title":"","body":"","url":"","tag":"","kind":""}
```

| Field | Type | Meaning |
|---|---|---|
| `v` | int | always `1` |
| `t` | string | `msg` (Teams notification), `alert`, `hb` (heartbeat), `pair` (pairing ping) |
| `id` | string | random UUID v4, used for de-duplication |
| `ts` | int | Unix seconds at the daemon when the message was created |
| `title`, `body` | string | notification title and text (`msg`, `alert`) |
| `url` | string | where a tap should go: an in-scope Teams URL (`msg`); empty → the receiver opens `https://teams.microsoft.com/v2/` |
| `tag` | string | Teams' notification tag (chat/thread id), used to group notifications |
| `kind` | string | alerts only: `session_expired`, `browser_dead`, `daemon_stopping` |

Unused fields may be omitted; receivers treat a missing string as `""` and ignore unknown fields.
The Go encoder emits fields in the order above, omits empty optional ones, and does not HTML-escape
(`<`, `>`, `&` appear literally); receivers must not depend on either.

## 4. Padding

```
plaintext = u16be(len(json)) || json || 0x00 …
```

padded to **1024** bytes if `len(json) + 2 ≤ 1024`, else to **2048** bytes. A sender guarantees the
document fits 2048 (`len(json) ≤ 2046`): it truncates `body` rune-wise to the longest prefix that
fits and appends `…` (U+2026); if an empty body is still too large it truncates `title` the same way,
then drops `tag`, `url` and `kind`. Truncation never splits a UTF-8 sequence.

A receiver rejects a plaintext whose size is not 1024 or 2048, whose declared length is 0 or exceeds
the buffer, that uses 2048 for a document that fits 1024, or whose padding bytes are not all zero.

## 5. Encryption

* ChaCha20-Poly1305 (RFC 8439), key `K`, 12-byte random nonce, AAD = ASCII `tbd:v1`.
* Sealed payload = `nonce (12) || ciphertext (1024|2048) || tag (16)` → 1052 or 2076 bytes.
* Go: `golang.org/x/crypto/chacha20poly1305`. Android: JCA `ChaCha20/Poly1305/NoPadding` (API 28+);
  plain JVMs (unit tests) name the same cipher `ChaCha20-Poly1305`.

## 6. FCM transport

FCM HTTP v1, always to the topic, never to a device token, **data** message only (no `notification`
block, so Android always hands it to the app):

```json
{"message":{"topic":"<topic>","android":{"priority":"high","ttl":"3600s"},"data":{"c":"<base64std(sealed)>"}}}
```

`ttl` is `21600s` for `hb`, `3600s` for everything else. `c` is 1404 or 2768 characters. FCM
documents 4096 bytes of data for most messages but 2048 for topic messages; if FCM rejects a
2768-character payload with 400 INVALID_ARGUMENT, the sender re-seals the same `id` truncated to the
1024 class (§4) and sends it again (FCM accepted 2768-character topic payloads when tested in
2026-11, so this is a safety net). Receivers must accept both sizes. What Google can observe: the
topic, the two possible sizes, and timing.

## 7. Receiver rules

1. base64-decode `c`, split nonce / ciphertext, decrypt with `K` and the AAD; on failure drop silently.
2. Unpad (§4) and parse the JSON; drop if `v ≠ 1`, `t` is unknown, or `id` is empty.
3. Drop if `ts` is more than 24 h in the past (exactly 24 h is still accepted).
4. Keep the last 256 accepted `id`s; drop duplicates.
5. Dispatch on `t`.

## 8. Test vectors

`vectors.json` contains: `secret_hex`, `code`, `display_code`, `qr_text`, `key_hex`, `topic`; for every
message type (and a Unicode and a truncated message) the nonce, the exact plaintext JSON, the padded
length and bytes, the ciphertext, the sealed `c` and the full FCM request body; parser inputs for the
code (valid and invalid); and sealed payloads that a receiver must reject (bad padding, wrong
version, unknown type, odd size, forged tag). The vector secret is public: never use it for pairing.
